# Ревью MR

Аргументы: `$ARGUMENTS`

Скрипты: `${CLAUDE_SKILL_DIR}/scripts/`. Крупные данные лежат в файлах каталога прогона, в контекст читай только нужные куски.

## 0. Жёсткие правила
- Рабочую копию пользователя не трогать: никаких `checkout`/`switch`/`stash`/`reset`/правок. Код ветки MR читать через `git -C <repo> show <head_sha>:<path>`, `git -C <repo> grep -n <pat> <head_sha>`, `git -C <repo> diff <start_sha> <head_sha> -- <path>`.
- Ничего не публиковать без явной команды пользователя («запушь …»).
- В публикуемом тексте — только суть замечания. Никаких подписей, «Claude», «Generated with», Co-Authored-By, эмодзи уровня, меток категорий. Ссылаясь на эталон, называть ветку явно (например `ref/migrate-to-ts/STR-766`).
- Субагентов не запускать — ревью делай сам, MR по очереди.

## 1. Цели
- Аргументы с MR (URL, `group/project!iid`, `project!iid`, `!iid`) → это цели.
- Без MR в аргументах → MR текущей ветки (`mr-fetch.sh` без аргумента).
- Затем ищи MR той же задачи в других проектах: `mr-related.sh <STR-N>` + ссылки на MR из `comments` задачи (`gantt-task.sh`, шаг 2). Если нашлись MR, не названные пользователем, спроси через AskUserQuestion (multiSelect), какие включить. Если MR были названы явно — не спрашивай, только упомяни найденные.

## 2. Сбор данных
Для каждой цели: `mr-fetch.sh <ref>` → печатает `meta.json` (run_dir, repo, diff_refs, task, счётчики тредов). В run_dir: `mr.json`, `discussions.json`, `commits.json`, `versions.json`, `diff.patch`, `diff.stat`.

Постановка: `gantt-task.sh <STR-N>` (один раз на задачу) → JSON: name, status, desc, assignees, parent/testTask/uiTask, subtasks, checklist, comments. Родитель и подзадачи дают контекст — что именно входит в эту задачу, а что нет. Если скрипт упал или задачи нет — опирайся на title/description MR и текст пользователя из аргументов; если суть задачи всё равно неясна — спроси у пользователя перед ревью «правильности решения».

Правила проекта: прочитай `CLAUDE.md` в корне `repo` (если есть) и память проекта — `~/.claude/projects/<repo-путь, где каждый не [A-Za-z0-9] символ заменён на ->/memory/*.md` (type feedback/project). Это источники конвенций для оси «чистота».

## 3. Ревью — четыре оси
Начни с `diff.stat`, затем `diff.patch` по файлам. Для понимания контекста читай файлы целиком на `head_sha`, вызывающих изменённых функций ищи `git grep` по `head_sha` (в текущем репо можно tokensave, но индекс отражает рабочую копию, а не ветку MR).

**A. Правильность решения**
- Реализовано ли то, что требует постановка, полностью и без лишнего; совпадает ли с MR в соседних проектах (контракт API ↔ клиент).
- Граничные случаи, null/undefined, ошибки и их коды, транзакции, гонки, идемпотентность.
- Миграции: обратимость `down`, enum/ALTER на mariadb (removeColumn сломан — нужен raw `ALTER TABLE`), данные в существующих строках.
- Обратная совместимость для старых клиентов/устройств, права доступа и проверки ролей/типов.
- Тесты: покрывают ли новые ветки логики; не ослаблены ли существующие.

**B. Чистота кода**
- Конвенции проекта (CLAUDE.md, память), нейминг, дублирование, мёртвый/закомментированный код, отладочные логи, магические значения вместо констант.
- Слои: репозиторий работает только со своей моделью; кеши — через Redis cache-репозитории; middleware импортируют сервисы через barrel.
- Типизация: TS без `any` без причины; JS-границы — JSDoc.
- Комментарии: устаревшие/врущие, лишние пересказы кода.

**C. Swagger** (только бэкенд-проекты: storm_apiv1, storm_microservices, storm-go и подобные; для фронта пропусти)
- Каждый новый/изменённый роут описан: storm_apiv1 — JSDoc `@swagger` в `*.route.(js|ts)` + `components` в `swagger.js`; NestJS — декораторы `@nestjs/swagger`.
- Body/params/query/enum-значения совпадают с Joi/DTO-валидацией; response — с реальным ответом контроллера.
- У каждого кода ошибки свой `examples` с реальным текстом (checkBearer: 403 'Access denied', 401, 404 'User or device not found' — через `BearerUnauthorized`/`BearerForbidden`/`BearerUserNotFound`); нет «Авторизация не требуется» на роутах с `checkBearer`.
- Удалённые/переименованные роуты убраны из документации.

**D. Прошлые треды** (`discussions.json`, все авторы)
- Для каждого треда с `position`: что изменилось в этом месте после комментария — `git diff <position.head_sha> <head_sha> -- <new_path>`; плюс ответы в треде.
- Статусы: ✅ исправлено · ❌ не исправлено · 💬 автор возразил (оцени, прав ли) · ⚠️ регресс (был resolved, но проблема вернулась/фикс откатили).
- Не дублируй в новых замечаниях то, что уже есть в открытом треде. Если тред не исправлен — это строка в таблице, а не новое замечание (кроме случая, когда нужен повторный комментарий — тогда отдельная находка с пометкой).

**Верификация**: каждую находку перед выводом перепроверь по коду на `head_sha` (строка существует, проблема реальна, не закрыта в другом месте). Сомнительное — уровень 💬 вопрос, а не утверждение.

## 4. Вывод
Запиши все находки в `~/.cache/mr-review/session-<STR-N или project-iid>/findings.json` — массив:
```json
{"id": 1, "project": "jungerschaft/storm_apiv1", "iid": 436, "run_dir": "...", "head_sha": "<diff_refs.head_sha>",
 "path": "models/x.ts", "new_line": 42, "old_line": null,
 "severity": "blocker|major|minor|question", "category": "решение|чистота|swagger|треды", "title": "кратко", "body": "текст для GitLab"}
```
- `new_line` — номер строки в новой версии (для добавленных/контекстных строк); `old_line` — только для удалённых строк. Без `path` — общее замечание к MR.
- `body` — на русском, вежливо и по делу: что не так → почему → как исправить (по возможности с кодом в ```-блоке). Не обращаться к автору по имени.

В чат — сквозная нумерация по всем MR:
```
## jungerschaft/storm_apiv1!436 — [STR-1026] add types to devices
Постановка: <1–2 строки, откуда взята>

### Прошлые треды
| Тред | Автор | Суть | Статус |
|---|---|---|---|
| models/device.model.ts:41 | AntonyPry | … | ❌ не исправлено |

### Новые замечания
1. 🔴 [решение] `routes/device.route.js:42` — кратко
   > текст ровно как уйдёт в GitLab
2. 🟡 [чистота] …

## jungerschaft/storm_client!381 — …
3. …
```
Уровни: 🔴 блокер · 🟠 важно · 🟡 мелочь · 💬 вопрос. В конце — путь к findings.json и подсказка: «Скажи, что запушить: `запушь 1,3,5-7` / `запушь все кроме 4`; правки текста — `в 3 …`».

Если замечаний нет — так и скажи, без выдумывания мелочей.

## 5. Публикация (только по команде)
1. Внеси правки пользователя в `body` нужных находок в findings.json (и только в них).
2. Dry-run: `post-comments.py <findings.json> <ids>` — проверь payload'ы (inline или note, текст без подписей).
3. Отправка: `post-comments.py <findings.json> <ids> --send`. ids: `1,3,5-7`, `all`, `all-4,9`.
4. Скрипт сам пропускает уже опубликованные, тексты с упоминанием ИИ и находки, если MR обновился после ревью (head_sha изменился) — в последнем случае перепроверь строки, обнови `head_sha`/номера и повтори.
5. Покажи пользователю список ссылок на созданные треды.

Скрипт `post-comments.py` вызывается только после явной команды пользователя опубликовать.
